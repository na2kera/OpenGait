### 1-4. FID_tt の「順序依存」の機構（※FID-anyには存在しない）
`train-test.py` の `calculate_fid` は `np.atleast_2d` の直後に `sigma2 += np.eye(...)*eps` を**コピーなしで**実行し、
`compute_fid_train_test` は **test の μ/Σ を1度だけ計算してループ内で使い回す**。
`np.atleast_2d` は2次元入力に対し**同一オブジェクト**を返すため、`test_sigma_inc` が破壊され、
train_roots の **k番目**では eps が **k回累積**している = **並び順が値を変える**。

コンテナ内での実挙動（numpy 1.23.5）:
```
atleast_2d は同一オブジェクト: True
nan_to_num はコピー: True
nan_to_num無し → 元配列が変化: 1.000001
nan_to_num有り → 元配列は不変: 1.0
```
→ **v1/v2/DINOv2版は `sigma1 = np.nan_to_num(sigma1)` で再代入しており累積しない。累積は FID_tt のみ。**

原本の `train_roots` は **id1〜id13 の順序のまま保存**されており、再現に必要な順序情報は失われていない。

## 3. 論点と現時点の結論

### 論点1: 「FID-any使用版 = faster」
**暫定固定**。id12 で記録値と採用条件が一意に再現した時点で確定に上げる。

> **id12 の証拠力の限界**（レビュー第2周 #11）: id12 で ALL が 26.4363 と一致すれば「**id12 は ALL 採用**」は確定するが、
> 集計表作成者が**全サブセットで一貫して ALL を選んだ**ことまでは直接証明しない。
> 報告では「id12 で ALL 採用を**確認**。他の混合条件サブセットも同じ採用規則と**推定**する」と、観測と推定を分けて書く。
> 余力があれば別の混合条件サブセット（id11 `nm1-bg1-cl1` 等）を1本追加すると更に強くなる。

### 論点2: FID_train_test を再計算するか
**手順1では再計算不要**。生値JSONとの26/26一致を採用し「監査済み・独立再実行免除」と記録する。

### 論点3: 高速化再実装（案B）
原本と数値同値実装を**別管理**し、**特徴 → 平均 → 共分散 → 各FID → 最終丸め値**の順に段階比較して同値を示せた場合のみ採用。

**保存が必要な順序（レビュー第2周 #3 により追加）**
原本 faster 版は被験者列挙が `os.listdir(root)`（未ソート）、`subjects` は辞書の挿入順、ペアは二重ループ順、平均はそのペア順の `np.mean` である。
現在は `/home/ryu` の同一ディレクトリを直接マウントしているため安定しているが、**データコピー・別ファイルシステム・並列化で順序が変わりうる**。
数値同値実装の要件に以下を追加する:
- 原本実行時の**被験者順**を保存する
- **ペアの生成順**を保存する
- 並列計算しても、結果を**原本のペア順へ戻してから平均**する
- FID_tt では **train root 順と eps の加算回数・順序**も保存する
- `eps` は原本と同じ回数・順序で加算する（`k*eps` の1回加算はビット一致しない可能性がある）

FID-any 75人版では**特徴抽出より CPU の sqrtm が支配的**なので、バッチ化だけでは解決しない。

### 論点4: コスト（→ コストゲートへ分離）
`sqrtm` 呼出数（レビューと計算が一致した確定値）:

| 対象 | sqrtm呼出数 | nm6比 |
| --- | --- | --- |
| nm6・25人（nm＋ALL） | 600 | 1.00 |
| 75人・1条件＋ALL | 5,550 | 9.25 |
| 75人・2条件＋ALL | 8,325 | 13.88 |
| faster原本の9サブセット合計 | 61,495 | 102.5 |
| 13サブセット合計 | 78,565 | 131.0 |

**採用する見積り（幅のみ。点推定は置かない）**
- 75人・1条件: **約4〜11時間**
- 13サブセット合計: **約3〜7日**

> **点推定を撤回**（レビュー第2周 #7）。v2で「sqrtm 約2.1秒/回 → 75人1条件で4.2h」としたが、
> 抽出とsqrtmの区間時刻を記録していないため根拠が弱い。実際 r2 は 01:31 開始で 01:47 頃から nm のペアFID に入り、
> 02:00 時点で 300 ペアを終えていない（2.1秒×300=10.5分より長い）。
> **id2 の総 wall で 75人・1条件は確定できるが、視野角3条件版まで同じ秒数/ペアで外挿できるとは限らない。**

### 論点5: 許容基準
- **歴史値との一致**: 元の表示と同じ **4桁文字列**で判定（数値換算で概ね `atol=5e-5`）
- **新環境内の安定性**: r2/r3 の揺れを別途記録する
- **print桁数の変更は行わない**（元の生値を復元できず、歴史値照合には効果が薄い）
- **MSD DINOv2**: `rtol=0, atol=5e-7`
- **MSD image / inception**: 二段階運用とする（レビュー第2周 #13）
  1. 第一判定: **ビット一致**（今回は一致）
  2. 不一致時: 即不合格とせず、**環境・順序を調査**する
  3. 歴史値の採否: 事前に定めた小さい許容差または表示精度で判定
  - `atol=0` を合格基準として固定すると、将来 4桁が同じでも低位1bitの変化で不合格になる。**「ビット不一致＝科学的に異なる値」と即断しない**旨を明記する

### 論点6: 71人問題
再計算では**現物の71人をそのまま使う**。分析側で「名目人数75」と「実画像被験者数71」を**分けて保持**する。
版特定には影響しないため手順1の阻害要因ではないが、**手順4の解釈を始める前の明示的ゲートとして登録**する。
欠落は 018 / 036 / 054 / 072（18の倍数）で、**原因は未特定**（§1-8）。

### 論点7: G-b の適用範囲（レビュー第2周 #2 の回答）
**採用スクリプト全体に適用する。免除規定は設けない。**
